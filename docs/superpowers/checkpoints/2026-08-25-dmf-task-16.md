## Deterministic optimization

Profiling proved the bottleneck was not FTS or PPR. The graph/candidate SQL was doing repeated scope/state lookups while processing known memory IDs.

Two changes were made without changing graph caps, ranking formulas, scope semantics, or adding any AI/vector dependency:

1. Graph expansion now fetches indexed edge rows first, then validates endpoint IDs in bounded ID-first batches and filters principal/project/state deterministically in JS.
2. Candidate memory loading now resolves known IDs via the primary-key path first, then applies principal/project/state filters deterministically in JS.

A cross-project explicit edge regression was added to prove the optimization does not weaken isolation.

## 1M decision

The master plan makes the 1M run conditional on local hardware/evaluation capacity. Actual 100k bulk seed took 730,159.532 ms (~12.17 minutes) and produced a ~130 MB DB. A linear 1M projection is ~7.3 million ms (~2.0 hours) and ~1.3 GB before additional benchmark churn. That exceeds the practical evaluation envelope for this workstation/session, so no fake/partial 1M result is claimed. The benchmark script supports `--count=1000000` for an explicit future dedicated run.
